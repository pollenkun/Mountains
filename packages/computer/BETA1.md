# Computer-use Beta 1

目标：日常能用。后台更快、被遮住的网页照常可读、系统下拉框不再卡住键盘、常见网页控件都能填、密码不经过模型。
基线：Codex 2026-10-19 晚的工作状态（提交 `2d8892a`）。分支 `preview-2/computer-use-beta1`，独立工作区，不影响主目录。

## 做了什么

**本机应用**
1. 原生窗口服务（`native/window-server.swift`，预编译通用二进制，运行时核对校验值）：
   硬件截图（失败退回录屏流）、网页引擎窗口保持可见、系统下拉框、菜单栏状态图标、不在屏幕上的窗口、恢复最小化窗口。
2. 下拉框和菜单栏菜单短暂占用键盘后归还，算成功并写明毫秒数；前台被换、焦点没恢复、原因不明仍算失败。
3. 后台按键前的等待从 0.12 秒改为默认 0.03 秒（`MOUNTAINS_FOCUS_SETTLE_MS`）。
4. `screen_read menubar` 列出状态图标，`screen_act menubar` 看菜单或按路径选。
5. `screen_act file_path`：打开、存储面板一次填好文件夹和文件名，按钮仍由模型按。
6. 读窗口时列出最小化或在别的桌面上的窗口；`screen_act unminimize` 在后台恢复最小化窗口。
7. `screen_look locate`：配置了定位模型（`computerUse.grounding`）时，按描述在截图里找控件并标出来。

**网页**
8. `web_read` 新参数：`console`、`network`、`wait_for`（不输入、只等文字出现）、`save_pdf`（只能存到工作区或下载目录）。
9. 修了往滑块里输入时文字跑进别的文本框的问题；滑块、日期、时间、颜色控件改为直接设值；颜色框和画布能读出来；画布可以按截图坐标点击。
10. 下拉框按显示文字选中、勾选框和单选框点击后都能读回确认。
11. 无窗口 Chrome 不回应滚轮时，2 秒后改用页面脚本滚动（原来要卡 15 秒再失败）。

**两边共用**
12. 保存的密码：`mountains secret add <名字> --domain <网站>`（或 `--app`），值存在系统钥匙串。模型写 `<secret>名字</secret>`，只在这个名字的网站（必须 https，本机地址除外）或应用里替换成真值；所有结果里的真值都换回占位符。
13. 本地操作记录：只记时间、工具、动作、应用名或网站域名、结果、用时；`mountains computer-history` 查看。
14. 说明书补上了以上用法。现在 3232 字，超过 Codex 验收设的 2500 字上限；按你“内容完整优先”的决定没有删。

## 已知风险

- 下拉菜单或状态图标菜单开着的零点几秒里，你按的键会进那个菜单。
- 硬件截图、保持可见、恢复窗口用的是 macOS 私有或辅助功能接口，每个大版本要重测；截图接口不在时自动退回录屏流。
- 保持可见会让被盖住的网页窗口继续出画面，稍微多耗电；Mountains 退出时恢复原状。
- 文件面板里两个框的标识（`PathTextField`、`saveAsNameTextField`）来自 Peekaboo 的实测，要在真机上再确认。
- 定位模型、cua-bench 还没有实际接上服务或跑过；虚拟机结果见文末。

## 审查意见（BETA1-REVIEW-20261019.md）怎么处理的

1. 下拉框坐标解析：真机已证明能用（上表）；仍改为接受任何 JSON 数字。
2. 存储面板：只用路径框自己的确认动作，不用回车；“位置”最多等 1.5 s，认文件夹名或它的显示名；对不上什么都不填。macOS 26 的面板没有路径框，完整路径一律拒绝；文件名改由窗口服务以 0.5 s 超时的请求写入并读回，可选 `press:true` 按存储。
3. 死锁接管：按可执行文件名找残留的 osascript 和 Mountains 自己的辅助程序；找到或查不准就不清锁。
4. 恢复最小化窗口抢前台：真机没有出现；若出现，焦点检查会切回原应用并报失败。
5. 密码：用过的值在本次对话后续所有结果里都被遮住（控制台、请求、读窗口）；少于 4 个字符的密码拒绝使用。子域名可用是有意设计。
6. 钉住的窗口：记录写到 `~/.mountains/window-server-pins.json`，崩溃后下一个窗口服务启动时先恢复。（遍历时删除在 Swift 里遍历的是副本，不会崩，仍改成先复制。）
7. 硬件截图：取到图后先拿自己的引用并复制，再释放列表。
- 菜单栏扫描单独一个进程，每个应用最多等 0.1 s；关掉的标签页删掉控制台和请求记录；滚轮检查只看指针下的那几层。

另外真机发现并修了：
- 读取展开的存储面板会因为另一个进程画的文件浏览器卡上几分钟：每次读取加时间上限（普通 4 s、完整 12 s），超时返回已读到的部分并说明。
- 早先两次真机运行把测试文件存进了面板记住的文件夹（`~/Documents/Codex/2026-10-17/sparxie-prop-v04/`），已移到废纸篓；测试应用的面板现在只在本次运行的临时文件夹里打开和写入。

## 点击是否生效由网页结果决定

原生 Chrome 探针中，辅助功能按下请求曾返回成功但没有点击。
实际 `web_read` 完整读取辅助信息后，按钮暴露了可执行的按下动作。
源码显示，该读取开启扩展属性，原生辅助树由此获得默认动作。
这是源码解释；本轮没有单独切换该辅助模式做对照。
完整测试走该动作，页面确认收到点击；没有派发后台指针。
因此不能把所有 Chrome 版本、窗口和辅助功能状态当成同一种情况。

仅创建窗口的独立对照中，Chrome 155 的后台指针没有效果。
Chrome 157 测试版使用同一指针路径成功，且前台和键盘均未改变。
Chromium 已修复非活动应用丢弃定向鼠标按下的问题。
这与对照结果相符，但不能证明所有旧版失败都只有这一原因。
官方来源：https://github.com/chromium/chromium/commit/212c026a848d25646e2c3c1fedfe0c27249367b7

保留原指针发送路径，没有增加抢前台重试。
后台网页点击后，若完整读回仍无变化，会明确报后台点击无效。
它保留已发送标记，禁止自动重试。
调用者应检查页面，再改用网页工具或得到授权后切到前台。

## 启动报告区分打断与真实归还

旧启动器把激活请求返回 true 当作归还成功。
独立图形任务中，普通激活和协作激活都不能证明前台回来。
WindowServer 方法可以归还原应用和键盘窗口。
现在只有观察到实际归还才计数；用户接管后停止恢复。
恢复不能抵消已经发生的抢占。

屏幕工具和网页工具都保留最终启动报告。
网页工具等报告完整后才返回，抢占或归还失败都报错。
取消、报告异常或启动后初始化失败，也不会自动再次启动。
普通 Chrome 的零抢占来自两步启动，并非事后抢回来。
